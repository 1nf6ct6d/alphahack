# Альфа Контекст

Персонализированная новостная аналитика для корпоративных клиентов банка. Решение связывает внешние события с проверяемыми признаками компании, объясняет возможный механизм влияния и предлагает следующий шаг с сохранением источников и условий.

Проект подготовлен для Alfa Hack 2026. В репозитории объединены backend, ML-библиотеки, контракты данных и материалы Prompt Engineer. Основной сценарий: выбор компании → обзор релевантных событий → подробный разбор → вопрос по разбору → обратная связь.

## 1. Назначение и состояние решения

Пользователь получает обзор для доступной ему компании в одном из двух фокусов:

- **CFO:** финансовые предпосылки, стоимость финансирования, денежные потоки.
- **CEO:** непрерывность деятельности, стратегические последствия, приоритет действий.

Фокус меняет аналитическое представление, но не права доступа. Связь компаний в данных сама по себе не открывает доступ к чужому профилю.

Реализованы HTTP API, SQLite с миграциями, импорт CSV, сборка профилей, ранжирование, сохранение обзоров и разборов, вопросы, feedback, импорт новостей и банковских PDF, учёт бюджета и кэш по контексту. Демо использует синтетические данные и работает без платных LLM-запросов.

Это рабочий backend MVP. Полное соответствие всем требованиям кейса и промышленная готовность не заявляются. Ограничения перечислены в разделе 13. Описанные ниже продуктовые метрики и регламент мониторинга — план измерения качества; наличие полноценной автоматической системы мониторинга не заявляется.

## 2. Архитектура

Система содержит четыре взаимодействующие части:

1. **Подготовка данных.** CLI импортирует CSV, новости и банковские материалы. `ml_features` рассчитывает признаки; backend собирает CompanyBusinessProfile и представления MLView, InterpreterView, UIView. Версии и происхождение данных сохраняются в SQLite.
2. **Персональный обзор.** FastAPI проверяет bearer-сессию и доступ к компании, загружает профиль и снимок новостей, вызывает `ml_ranking` и сохраняет до пяти кандидатов. GET читает сохранённый обзор; refresh не запускает массовую генерацию полных разборов.
3. **Подробный разбор.** Сервис получает основания выбранного события и проверенные банковские фрагменты. При включённом LLM резервирует бюджет, запрашивает текст и проверяет структуру генерируемой части и ссылки. Сохранённый результат переиспользуется в том же контексте.
4. **Диалог и качество.** Вопросы закрепляются за пользователем, компанией, фокусом и версией insight. Feedback сохраняется с историей изменений и используется для разбора ошибок.

SQLite работает в WAL-режиме на одном хосте. Профили и снимки версионируются; обновление новости не меняет содержимое старого снимка. Контекст кэша учитывает компанию, scope доступа, профиль, новости, банковский корпус, версии модели/промпта/правил и час расчёта. Lease в БД ограничивает параллельное создание одного разбора.

Frontend подключается к HTTP API. Пользовательский интерфейс и сбор событий его показов/открытий не входят в backend-пакет, описанный в этом README.

## 3. Используемые компоненты

- `backend/` — FastAPI, конфигурация, авторизация, repository, application services, импорты, OCR и LLM gateway.
- `backend/migrations/` — SQL-миграции с контрольными суммами.
- `ml_audit/` — аудит структуры CSV, пропусков, повторов и конфликтов.
- `ml_features/` — платёжные/групповые признаки, точные суммы и DerivedMetric. Backend вызывает существующие функции и не дублирует финансовую математику.
- `ml_ranking/` — детерминированный отбор и ранжирование нормализованных событий с основаниями и ограничениями.
- `ml_evaluation/` — Precision, Recall, nDCG и сравнение с baseline на замороженных наборах.
- `schemas/`, `rules/`, `prompts/` — контракты, правила и промпты команды.
- `bce_lab/` — самостоятельный лабораторный стенд проверки BCE-промптов; полный BCE-процесс не подключён к runtime backend.
- `tests/` — модульные, контрактные и интеграционные тесты. `fixtures/invalid` содержит намеренно некорректные примеры для отрицательных проверок.
- `config/backend.env.example` — шаблон конфигурации.
- `scripts/` — HTTP smoke, проверка OCR, Windows-запуск и упаковка ZIP.
- `docs/` — документация, OpenAPI, передача ML и результаты разработческой проверки.

Технологии: Python 3.14, FastAPI, Pydantic, Uvicorn, SQLite, jsonschema, referencing, tzdata. Для тестов используется HTTPX. Docker-образ устанавливает Poppler и Tesseract с языками `rus+eng`.

Прямые зависимости заданы в `requirements-backend.txt` и `requirements-ml.txt`; транзитивные версии ограничены `requirements.lock.txt`. Компоненты и лицензии описаны в [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).

## 4. Требования к окружению

Рекомендуемый запуск: Docker Desktop с Linux containers и Docker Compose, поддерживающим `--wait`. Первая сборка требует доступ к реестру образов и репозиториям зависимостей. Последующее синтетическое демо не требует доступа к LLM.

Для native-запуска нужны:

- Python 3.14 и pip; Windows-команды ниже рассчитаны на PowerShell.
- Локальная папка с правом записи для SQLite и свободный порт.
- Для PDF/OCR: `pdfinfo`, `pdftotext`, `pdftoppm`, `tesseract` и языки rus/eng; в Docker они установлены.
- Для реальной генерации: HTTPS endpoint совместимого API, ключ, разрешённый model ID и подтверждённая верхняя стоимость вызова.

Стандартный порт приложения — 8080. В примерах используется 18080, чтобы обойти возможное резервирование 8080 Windows. SQLite размещайте на локальном диске или Docker volume; активная БД на сетевом/синхронизируемом диске, включая OneDrive, не является рекомендуемой конфигурацией.

## 5. Запуск через Docker

Выполняйте команды из корня репозитория, где находится `docker-compose.yml`:

```powershell
$env:ALFA_PORT = "18080"
docker compose up --build -d --wait
docker compose ps
```

Ожидаемое состояние API — `healthy`. Если ваша версия Compose не поддерживает `--wait`, запустите с `-d` и проверьте состояние через `docker compose ps`.

- Swagger UI: <http://127.0.0.1:18080/docs>
- OpenAPI: <http://127.0.0.1:18080/openapi.json>
- Готовность: <http://127.0.0.1:18080/health/ready>
- Возможности конфигурации: <http://127.0.0.1:18080/meta/capabilities>

В Swagger нажмите **Authorize** и вставьте `demo-test-a` без слова Bearer. Для обычного HTTP-запроса используйте `Authorization: Bearer demo-test-a`.

Тестовые учётные записи:

- TEST_A → U_5639, токен `demo-test-a`.
- TEST_B → U_123123, токен `demo-test-b`.

Токены предназначены для локального демо. Данные синтетические; реальные имена компаний по непрозрачным ID не восстанавливаются.

Логи и остановка:

```powershell
docker compose logs -f api
docker compose down
```

БД сохраняется в named volume. `docker compose down -v` удаляет volume с данными и для обычной остановки не используется. Если выбранный порт недоступен, измените `ALFA_PORT`; внутри контейнера приложение продолжит слушать 8080.

## 6. Запуск без Docker

```powershell
py -3.14 -m venv .venv_backend
.\.venv_backend\Scripts\python.exe -m pip install -r requirements-backend.txt
.\.venv_backend\Scripts\python.exe -m pip check
$env:ALFA_DEMO_SEED = "1"
$env:ALFA_ADMIN_TOKEN = "demo-admin"
$env:ALFA_CORS_ORIGINS = "http://localhost:5173,http://localhost:3000"
.\.venv_backend\Scripts\python.exe -m backend.cli serve --host 127.0.0.1 --port 18080
```

Терминал с сервером должен оставаться открытым; Ctrl+C останавливает приложение. Активация virtualenv не обязательна. Миграции применяются при старте. При `No module named fastapi` проверьте, что используется Python из `.venv_backend`.

На Linux/macOS используйте доступный `python3.14`, а Python окружения находится в `.venv_backend/bin/python`. В native-режиме OCR-инструменты устанавливаются отдельно.

## 7. Конфигурация и переменные окружения

Python CLI читает переменные процесса и сам не загружает dotenv. Compose читает переменные оболочки и корневой `.env`:

```powershell
Copy-Item config/backend.env.example .env
```

Заполните файл локально и не добавляйте секреты в Git. Переменные оболочки имеют приоритет над `.env` при подстановке Compose.

### Приложение и доступ

- `ALFA_ENV` — `development`, `test`, `production`; default `development`. Production требует pepper, но сам флаг не означает промышленную готовность.
- `ALFA_PORT` — публикуемый порт Compose; default 8080. Native-порт задаётся `serve --port`.
- `ALFA_DATABASE_PATH` — SQLite; native default `data/backend.sqlite3`. В Compose закреплён `/app/data/alfa_context.db` с persistent volume.
- `ALFA_AUTH_TOKEN_PEPPER` — постоянный серверный секрет от 24 UTF-8 байт для HMAC токенов. До выдачи реальных сессий замените development-значение. Смена pepper требует перевыдачи токенов.
- `ALFA_DEMO_SEED` — `1` включает синтетическое демо, `0` используется с реальными данными. Seed отказывается работать поверх недемо-профилей и реальных новостей.
- `ALFA_DEMO_TOKENS` — пары `TEST_A=tokenA,TEST_B=tokenB` с разными токенами.
- `ALFA_ADMIN_TOKEN` — секрет служебных импортов, заголовок `X-Admin-Token`. В пользовательский frontend не передаётся.
- `ALFA_CORS_ORIGINS` — разрешённые origin через запятую. Native default — без CORS-разрешений; Compose содержит локальные development origins.
- `ALFA_SQLITE_TIMEOUT_SECONDS` — ожидание SQLite, default 10 секунд.

### Источники, OCR и бюджет

- `ALFA_ALLOWED_SOURCE_HOSTS` — точные имена разрешённых новостных хостов; default `www.cbr.ru,cbr.ru,www.interfax.ru,interfax.ru`.
- `ALFA_BUDGET_TIMEZONE` — часовой пояс дневной квоты; default `Europe/Moscow`.
- `ALFA_DAILY_BUDGET_RUB` — внешний ориентир, default 500 рублей.
- `ALFA_INTERNAL_BUDGET_RUB` — порог резервирования, default 450 рублей, не выше внешнего лимита.
- `ALFA_PDFINFO_BIN`, `ALFA_PDFTOTEXT_BIN`, `ALFA_PDFTOPPM_BIN`, `ALFA_TESSERACT_BIN` — необязательные пути к OCR-инструментам; иначе используется PATH.

Compose передаёт только переменные, перечисленные в его `environment`. В текущем файле timezone, SQLite timeout и бюджет используют defaults. Для их переопределения в контейнере добавьте соответствующие строки в `docker-compose.yml`: наличие переменной только в `.env` не передаёт её контейнеру автоматически.

### LLM

- `ALFA_LLM_ENABLED=0` — без платной генерации; `1` включает шлюз.
- `ALFA_LLM_BASE_URL` — HTTPS API base, например `https://provider.example/v1`; клиент добавляет `/chat/completions`.
- `ALFA_LLM_API_KEY` — ключ API на сервере.
- `ALFA_LLM_MODEL` — точный API model ID, разрешённый организаторами и доступный аккаунту.
- `ALFA_LLM_MAX_CALL_KOPECKS` — подтверждённая верхняя стоимость вызова в копейках, положительное целое число.

При включённом LLM обязательны параметры подключения и стоимости. Верхняя оценка рассчитывается по подтверждённому тарифу для запроса до 192 KiB и до 1800 output tokens, включая тарифицируемые reasoning tokens. Случайное число не является подтверждённой оценкой.

До вызова БД атомарно проверяет `confirmed + reserved + next_max <= internal_limit`. Сейчас в журнал списывается консервативная верхняя стоимость, включая неоднозначный timeout; это не точный счёт провайдера. Usage с tokens и длительностью сохраняется, когда доступен. Расход лаборатории/других обращений с тем же ключом учитывается отдельно. Автоматических повторных платных вызовов нет.

## 8. API и интеграция frontend

Пользовательские маршруты требуют bearer-сессию. Актуальный контракт — `/openapi.json`.

- `GET /companies` — разрешённые компании; текущий список содержит `items[].id` и `display_name`.
- `GET /companies/{company_id}` — профиль и три представления.
- `GET /companies/{company_id}/overview?analytic_focus=CFO` — сохранённый обзор.
- `POST /companies/{company_id}/overview/refresh` — подготовка обзора, тело `{"analytic_focus":"CFO"}`.
- `POST /companies/{company_id}/insights` — один разбор по `analytic_focus` и `event_id` выбранного кандидата.
- `GET /insights/{insight_id}` — сохранённый разбор.
- `POST /insights/{insight_id}/questions` — `question` и `conversation_id` либо null.
- `PUT /insights/{insight_id}/feedback` — `rating`, `reason`, необязательный `comment`.

`rating`: `useful`/`not_useful`. `reason`: `relevant`, `irrelevant`, `factual_error`, `outdated`, `unclear`, `other`. Для продолжения диалога передайте возвращённый `conversation_id`.

Overview различает `not_prepared`, `empty` и `ready`. При `not_prepared` нужен refresh. GET не запускает LLM. Insight имеет отдельный статус достаточности данных; состояние поиска банка независимо. На frontend смена компании/фокуса сбрасывает открытый диалог, а запоздалые ответы сверяются с текущим контекстом.

Коды ошибок: 400 — запрос; 401 — сессия; 404 — отсутствующий/недоступный ресурс без раскрытия чужих объектов; 409 — подготовка либо параллельная операция; 429 — бюджет; 503 — зависимость. Timeout не является пустой выдачей.

Служебные `/admin/events`, `/admin/news/url`, `/admin/news/feed`, `/admin/bank-reports`, `/admin/budget` требуют `X-Admin-Token`. Полные примеры — [BACKEND.md](docs/BACKEND.md).

## 9. Пошаговый сценарий проверки

### Автоматический smoke

После Docker-запуска:

```powershell
docker compose exec -T api python scripts/smoke_backend.py
docker compose exec -T api python -m scripts.verify_ocr
```

Первый скрипт проверяет реальный HTTP внутри контейнера; второй — настоящие Poppler/Tesseract на временном синтетическом PDF. Ожидаются строки `PASS`.

С хоста:

```powershell
py -3.14 scripts/smoke_backend.py --base-url http://127.0.0.1:18080
```

Smoke рассчитан на демо-пользователей и создаёт тестовый feedback. Запускайте его на демо-БД с выключенным LLM, если нужны только бесплатные проверки.

### Ручная проверка через Swagger

1. `GET /health/ready` — сервис готов.
2. Авторизуйтесь `demo-test-a`; `GET /companies` должен вернуть только U_5639.
3. Откройте профиль U_5639: проверьте profile/views и ограничения данных.
4. Выполните POST overview/refresh с CFO: получите кандидатов с основаниями и условиями.
5. Возьмите `event_id` из списка, выполните POST insights. Проверьте interpretation, sources, evidence, next_steps и статус поиска банка. Отсутствующий демо-корпус банка должен отображаться отдельным состоянием, без вымышленной позиции.
6. Повторите создание того же insight в том же контексте: ожидается сохранённый `insight_id`.
7. Задайте «На каких признаках основан вывод?» и «Что проверить дальше?». Во втором запросе передайте `conversation_id` первого. Детерминированный режим поддерживает основания, условия и следующий шаг.
8. Отправьте `{"rating":"useful","reason":"relevant"}` в feedback. Повторный PUT обновляет действующую оценку с историей.
9. Переключитесь на CEO: проверьте отдельный контекст и адресованный роли следующий шаг.
10. Авторизуйтесь `demo-test-b`; запросите U_5639 и insight первого пользователя: ожидается 404. Собственная U_123123 должна оставаться доступной.

### Программные тесты

```powershell
.\.venv_backend\Scripts\python.exe -m pip install -r requirements-test.txt
.\.venv_backend\Scripts\python.exe -B -X utf8 -m unittest discover -s tests -p "test_*.py"
.\.venv_backend\Scripts\python.exe -m pip check
```

В разработческом прогоне 26.10.2026 прошли 316 тестов, включая запуск из распакованного backend ZIP. Docker HTTP-сценарий и OCR проверены отдельно. Это проверка программы, не доказательство полезности на реальных пользователях. После изменений исходников проверки повторяются. См. [RELEASE_VERIFICATION.md](docs/RELEASE_VERIFICATION.md).

ML-пример: `python -B -X utf8 -m examples.ml_library_usage`. `tests/validate_all.py` пересоздаёт fixtures, `bce_lab selftest` создаёт локальные результаты: выполняйте их в отдельной временной копии. Платный лабораторный `bce_lab run --live` для обычного запуска backend не нужен.

## 10. Реальные данные и источники

Пример для отдельной native-БД:

```powershell
$env:ALFA_DEMO_SEED = "0"
$env:ALFA_DATABASE_PATH = "data/private/live.sqlite3"
$env:ALFA_AUTH_TOKEN_PEPPER = "ЗАМЕНИТЕ_ПОСТОЯННЫМ_СЛУЧАЙНЫМ_СЕКРЕТОМ_ОТ_24_БАЙТ"
.\.venv_backend\Scripts\python.exe -m backend.cli migrate
.\.venv_backend\Scripts\python.exe -m backend.cli import-datasets --data-dir data/private/input
.\.venv_backend\Scripts\python.exe -m backend.cli import-profile --company-id U_5639 --companies data/private/input/df_Uid_data_hack.csv --payments data/private/input/df_Uid_payment_hack.csv --as-of-date 2026-10-26
.\.venv_backend\Scripts\python.exe -m backend.cli create-user --user-id TEST_A --company-id U_5639 --hours 24 --show-token
```

В `data/private/input` ожидаются `df_Uid_data_hack.csv`, `df_Uid_payment_hack.csv`, `df_Fid_Uid_link_hack.csv`. Дата среза должна соответствовать данным. Person links импортируются для происхождения, не дают прав доступа. ML-сборка использует исходные CSV; staging хранит raw cells, нормализованные значения и ошибки для аудита.

Пропуск не превращается в false. Неизвестный получатель входит в знаменатель внешних платежей; self-payment учитывается отдельно. Конфликтующие профили не разрешаются произвольно. Платёж не доказывает поставку. Аддитивность строк — явное допущение, отключаемое `--rows-are-not-additive`. Без периода и единиц нельзя заявлять годовую динамику или точный финансовый эффект.

Новости импортируются через `import-feed`/`import-url` либо admin API. Сначала сохраняется текст с консервативным `event_type=other`. Для ранжирования нужна нормализация: `normalize-event` с включённым LLM либо импорт проверенного event JSON. RSS без доступной статьи не считается полным текстом. URL проверяются по точному allowlist, redirect и публичному IP; соединение привязывается к проверенному адресу.

Банковский PDF проходит `import-bank-pdf ... --review-json data/private/report.review.json`, ручную проверку страниц/дат/процентов, затем `import-bank-report`. Только `verified=true` участвует в поиске. Ключи, банковские CSV/PDF и рабочая БД в Git не добавляются. Подробные команды и форматы — [BACKEND.md](docs/BACKEND.md).

## 11. Продуктовые метрики и оценка качества

### Требование организаторов

> Здравствуйте! Да, предложить продуктовые метрики и описать процесс регулярного мониторинга качества обязательно. При этом конкретный список метрик не установлен, вы определяете его самостоятельно. Доказывать их эффективность на реальных пользовательских данных не требуется, но важно объяснить, как метрики будут рассчитываться и использоваться для оценки качества решения

Ниже определены предлагаемые показатели и их использование. Эффективность на реальных пользователях не заявляется. Приведённые пороги — первоначальные правила команды для пилота, а не доказанные отраслевые нормы.

### Общие правила расчёта

Для каждой метрики фиксируются окно времени, размер выборки, знаменатель и версия решения. Нулевой знаменатель означает `N/A`. Синтетическое демо, офлайн-разметка и реальные пользовательские сессии анализируются раздельно. Срезы: CFO/CEO, компания или разрешённый агрегат, версия модели/промпта/данных и режим банковской аналитики.

Продуктовое окно — последние 7 дней в сравнении с предыдущими 7. Технические сбои и бюджет проверяются ежедневно. Повторные отправки и retries не увеличивают число логических действий. Пользователи и компании учитываются по серверным ID без восстановления реальных имён.

### Продуктовые показатели

1. **Полезность разборов.** `useful / (useful + not_useful) × 100%`. Источник — действующие записи `feedback`; на user/insight/version берётся последняя оценка, история не увеличивает число голосов. Показатель используется для выявления неудачных механизмов, фокусов и версий. Предварительный сигнал исследования: падение от 10 процентных пунктов при минимум 20 оценках в каждом сравниваемом окне. Это сигнал разбора, не доказательство причины изменения.
2. **Охват оценкой.** `уникальные пары user/insight/version с feedback / такие пары с просмотром insight × 100%`. Числитель — feedback, знаменатель — планируемое frontend-событие `insight_viewed`. Без сбора просмотров метрика не рассчитывается; созданные разборы не подменяют просмотры. Рассматривается вместе с полезностью, чтобы видеть самоотбор отвечающих пользователей.
3. **Успешность пользовательской задачи.** `успешно выполненные задания / все попытки × 100%`. Участник должен выбрать компанию, найти событие, объяснить основание, открыть источник и назвать следующий шаг без подсказки. Источник — протокол сценарного наблюдения с отметками по шагам. Использование: проверять понятность продукта; при сравнении версий задания одинаковы, помощь модератора отмечается отдельно.
4. **Конверсия в разбор.** `уникальные сессии с открытием карточки / сессии с просмотром непустого обзора × 100%`. Нужны будущие `overview_viewed`, `insight_viewed`, session ID и context ID. Пустые обзоры учитываются отдельно. Использование: оценивать привлекательность/понятность предложений; рост открытий без роста полезности не считается самостоятельным успехом.
5. **Время до полезного результата.** Медиана и p95 интервала от начала задания/показа обзора до подтверждения полезного разбора либо успешного выполнения задания. Источник — сценарный протокол или связанная frontend-телеметрия. Незавершённые попытки показываются отдельной долей. Метрика помогает находить трение интерфейса и отличается от серверной задержки.

### Качество отбора и объяснений

1. **Релевантность среди показанного.** `релевантные показанные события / все показанные события` по экспертной оценке пар компания/фокус/событие на замороженном пуле. Пустая выдача не считается 100% качественной; отдельно фиксируется, были ли релевантные события в пуле и сколько пропущено.
2. **Precision@5, Recall@5, nDCG@5.** Существующий `ml_evaluation` использует независимую разметку: Precision — фиксированный знаменатель 5; Recall — все релевантные события заданного пула; nDCG — градуированную релевантность и порядок. Поэтому Precision@5 отличается от доли релевантных среди фактически показанных при выдаче короче пяти. Использование: сравнивать версии с baseline на одном пуле и контролировать полноту. Подробные формулы/`N/A` — [ml_evaluation/README.md](ml_evaluation/README.md).
3. **Покрытие основаниями.** `проверяемые утверждения с разрешимыми evidence IDs / все проверяемые утверждения × 100%`. Проверяются evidence, доступный источник и локатор. Для принятого контрольного набора цель — 100%. Наличие ссылки не доказывает смысловую правильность утверждения.
4. **Смысловая подтверждённость и корректность признаков.** Отдельно: `утверждения, подтверждённые первоисточником / все проверенные утверждения` и `использованные значения, совпавшие с данными / все проверенные значения`. Источник — независимая ручная проверка с сохранением claim, цитаты/поля, решения и причины. Неясные случаи не считаются подтверждёнными. Критическая выдумка факта, суммы, обязанности или позиции банка блокирует соответствующий демонстрационный результат независимо от среднего балла.
5. **Уместность аналитики банка.** `разборы с подтверждённым уместным вкладом банка / все проверенные разборы, заявляющие такой вклад`. Проверяются дата, страница, цитата и связь с выводом. Завершённый поиск без подходящего отчёта не является ошибкой; недоступный корпус не равен завершённому поиску. Метрика выявляет случайно прикреплённые обзоры и ложную атрибуцию мнения банка.

Офлайн-пул размечается до просмотра оцениваемой выдачи. Публикации об одном событии не разделяются между development и held-out. Автор конкретного промпта не является единственным оценщиком его результатов. Для ручного разбора предлагается рубрика: релевантность, механизм, основания, следующий шаг, неопределённость — по 0/1/2. Предварительный внутренний порог — 8/10 при отсутствии критических ошибок. Разногласия сохраняются и разрешаются по первоисточникам.

### Технические показатели

- **Доля ошибок:** `технически неуспешные запросы / все запросы операции`. Отдельно показываются 5xx, ожидаемые 4xx, 429 бюджета и 409 параллельной операции. Полный знаменатель потребует журнала HTTP/reverse proxy; `usage_ledger` не заменяет счётчик всех запросов.
- **Задержка:** p50/p95 от принятия HTTP-запроса до ответа, отдельно overview/generation/question. Сейчас `usage_ledger.elapsed_ms` отражает учитываемую операцию вокруг LLM, не весь пользовательский путь и не все запросы. До HTTP-телеметрии полный latency измеряется контрольным прогоном.
- **Расход и резерв:** сумма `usage_ledger.cost_kopecks` плюс активные `budget_reservations` по дате бюджета. Остаток сравнивается с внутренними 450 рублями и кабинетом провайдера. Timeout и незакрытые резервы разбираются отдельно. Верхнеоценочный журнал не выдаётся за фактический биллинг.
- **Покрытие источников:** доля обнаруженных URL с полным текстом, доля metadata-only/ошибок и дата последнего успешного импорта по источнику. Источники расчёта — журнал batch, imports/errors и `source_documents`. Просадка покрытия отделяется от ухудшения ранжирования.

### Доступные данные и план внедрения

Уже сохраняются feedback с историей, версии insight/контекста, сообщения, источники, imports/errors и budget/usage. Есть офлайн-оценка ранжирования, HTTP smoke и тесты доступа. Эти данные доступны для ручного анализа и отчётных запросов.

Автоматического продуктового dashboard, frontend-событий просмотров, полного журнала HTTP-метрик, scheduler мониторинга и уведомлений в текущем backend нет. Метрики с такими знаменателями описаны как план измерения. Наличие таблицы не означает, что показатель уже автоматически рассчитывается.

## 12. Процесс регулярного мониторинга качества

Это предлагаемый регламент. На хакатоне он выполняется командой вручную; расписание не означает уже настроенную автоматизацию.

### Перед каждой демонстрацией и релизом

1. Зафиксировать commit, версии модели/промпта/правил, профиль, news snapshot и состав банковского корпуса.
2. Запустить тесты, HTTP smoke и изоляцию TEST_A/TEST_B; визуально проверить используемые OCR-фрагменты.
3. Повторить сохранённые проблемные случаи и контрольный набор на тех же входах, сравнить с предыдущей версией.
4. При ошибке доступа, выдуманном критическом факте или неподтверждённой позиции банка исключить соответствующий результат из демонстрации до исправления и повторной проверки.

### Ежедневно в пилоте

Дежурный backend проверяет доступность, ошибки импорта/генерации, состояние источников, резервы и остаток бюджета. Product/UX просматривает новые отрицательные отзывы; ML/Prompt Engineer разбирает неверные факты, нерелевантность и источники. Все критические обращения проверяются независимо от размера выборки. При небольшом числе наблюдений показываются количества случаев без заявлений о статистическом тренде.

### Еженедельно в пилоте

Команда рассматривает полезность и охват оценкой за 7 дней, сравнивает с предыдущим окном и проверяет ориентировочно 12–20 разборов. Выборка включает положительные, отрицательные и неоценённые результаты, оба фокуса, разные компании, режимы банка и отказы. При малом потоке проверяются все доступные случаи с указанием фактического числа.

Выполняются независимая проверка оснований и офлайн-сравнение ранжирования. Итог — воспроизводимые дефекты, приоритеты, ответственные, решения об исправлении/ограничении и новые регрессии. Промпт, модель и пороги не изменяются автоматически по одному отзыву.

### Цикл разбора ошибки

`new → in_review → resolved`. В БД есть feedback ID, серверный user ID, company ID, insight/version, причина, комментарий и timestamps; история оценок сохраняется. Triage и смена состояния выполняются вручную уполномоченным участником; отдельной admin-панели нет.

Для воспроизведения фиксируются исходный контекст, запрос, версия результата, evidence, ожидаемое поведение и категория: данные, извлечение, ранжирование, генерация, интерфейс или доступ. Ответственные: backend — права/сохранение/контекст; ML — признаки/отбор; Prompt Engineer — текст/проверки; Product/UX — полезность и понятность. Закрытие требует повтора примера и регрессионной проверки либо документированного ограничения.

Предварительные сигналы: любая утечка доступа или критическая фактическая ошибка — немедленный разбор; три подряд 5xx в контрольном прогоне — проверка до следующего демо; падение полезности при достаточной выборке — исследование причин; остаток бюджета меньше максимума следующего вызова — отказ от платного вызова с понятным статусом. Это правила процесса, не готовые автоматические alert rules.

## 13. Известные ограничения

- Агентный процесс пока фиксирован; полноценное планирование по пробелам и адаптивный повторный поиск требуют реализации.
- BCE-промпты и лаборатория сохранены, но полный BCE-процесс с экспертной KB не подключён к профилированию. По умолчанию используется `kb_fallback`; runtime narrative/normalization gateway имеет отдельную версию промпта.
- Банковский поиск лексический; смысловая уместность вкладов и полное правило `bank_requirement` требуют доработки. OCR не заменяет проверку таблиц, графиков, дат и процентов.
- Полный валидатор выходного Insight 2.2 и точное согласование всех полей исходного ТЗ не завершены. Проверка генерируемой части и ссылок не равна полной контрактной приёмке.
- Model ID выбирается в конфигурации; программный allowlist моделей и запрет synthetic-источников в production пока не реализованы. Демо-секреты предназначены только для локальной проверки.
- Сохраняются текст, страницы и hash PDF; защищённое хранение/выдача исходных PDF и изображений требуют доработки.
- Реальные API-ключи, банковский корпус и независимая разметка подключаются командой. Платный API организаторов в разработческой проверке не использовался.
- Пользовательский frontend и автоматическая система продуктового мониторинга в описанный backend-пакет не входят. Метрики и регламент выше объясняют будущие расчёты и использование, без заявления эффективности на реальных пользователях.
