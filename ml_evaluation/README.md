# ML-3A — воспроизводимая оценка ранжирования

Пакет сравнивает неизменённый ML-2A с простым отраслевым baseline. Оба получают один замороженный пул кандидатов, одинаковый k и одинаковую независимую разметку. Новые модели, обучение, оптимизация ранжирования и обращения к LLM не выполняются.

Реальный набор пока ожидает независимой разметки. Синтетические ожидания служат только проверке инфраструктуры. Они не являются оценками реальных людей и не подтверждают качество ранжирования на настоящих новостях.

## Запуск

```powershell
.\.venv_win\Scripts\python.exe -B -X utf8 -m ml_evaluation
.\.venv_win\Scripts\python.exe -B -X utf8 -m ml_evaluation --dataset ml_evaluation/templates/real_dataset.json --split held_out --output-dir reports/real_evaluation
.\.venv_win\Scripts\python.exe -B -X utf8 -m unittest discover -s tests -p "test_news_evaluation.py"
```

Без `--dataset` выполняется только синтетическая демонстрация на development. Параметры: `--k` (по умолчанию 5), `--relevant-threshold` (1 или 2), `--split` (development или held_out), `--output-dir`. Реальный шаблон пуст, поэтому его отчёт имеет статус `awaiting_independent_annotation`, нулевые счётчики и N/A вместо метрик. Запуск не создаёт новости или оценки для заполнения шаблона.

Локальные отчёты `reports/ml3a_news_ranking_evaluation.json` и `.md` исключены через `.gitignore`. Для собственного output-dir правила исключения следует применять в месте хранения данных. Предпочтительный каталог для реальных замороженных наборов и их отчётов — уже исключённый `data/raw/`.

## Python-интерфейс

```python
from ml_evaluation import evaluate_dataset, load_dataset
from ml_evaluation.reporting import write_reports

dataset = load_dataset("data/raw/evaluation/v1.json")
report = evaluate_dataset(
    dataset, split="held_out", k=5, relevant_threshold=1
)
write_reports(report, "data/raw/evaluation/reports/v1")
```

`evaluate_ranking`, `precision_at_k`, `recall_at_k`, `ndcg_at_k` и `dcg` доступны отдельно для математических проверок. `industry_only_rank` возвращает список event_id. `evaluate_dataset` и `validate_dataset` не изменяют переданные объекты.

Для персонализации вызывается существующий `ml_ranking.rank_news(ml_view, events, company_profile=..., analytic_focus=..., top_k=..., as_of=...)`. Его правила, веса, модели и контракты сохранены. Профиль и MLView по-прежнему готовит Backend; контейнер contexts хранит их снимки, а не создаёт новый бизнес-профиль.

## Метрики

Один запрос — компания, замороженная версия профиля, фокус и пул новостей. Разметка имеет целые степени 0, 1, 2:

| Степень | Смысл |
|---|---|
| 0 | Обоснованного бизнес-механизма нет |
| 1 | Есть условный механизм, существенная предпосылка неизвестна |
| 2 | Есть подтверждённое основание компании и поддержанный механизм |

Это степени релевантности, не вероятность и не размер финансового эффекта. По умолчанию релевантна степень ≥ 1. Порог 2 позволяет отдельно оценить нахождение подтверждённых событий; он не меняет градуированные веса nDCG.

**Precision@k** = число релевантных в первых k / k. Знаменатель всегда k, даже если система вернула меньше результатов или сам пул меньше k. Например, два релевантных результата при k = 5 дают 0,4. Пустые позиции не заполняются новостями.

**Recall@k** = число найденных релевантных в первых k / число всех релевантных в размеченном кандидатном пуле. Это полнота относительно данного пула, а не всего интернета. Если релевантных по порогу нет, Recall = N/A.

**DCG@k** = Σ от позиции i = 1 до k: `(2^grade_i − 1) / log2(i + 1)`. Отсутствующие позиции дают нулевой вклад. Веса степеней: 0, 1, 3. **IDCG@k** использует все оценки пула в идеальном убывающем порядке. При равных степенях порядок стабилизируется event_id. **nDCG@k** = DCG / IDCG. При IDCG = 0 результат N/A. Если все оценки 1 и бинарный порог 2, Recall будет N/A, но nDCG остаётся вычислимым по градуированным оценкам.

Пример ручной проверки: идеальный порядок степеней `[2, 1, 0]` имеет DCG `3 + 1/log2(3)`. Обратный `[0, 1, 2]` имеет DCG `1/log2(3) + 3/2`. Их отношение — nDCG обратного порядка при k = 3. Эти значения проверяются тестами независимо от ранжировщика.

Пустой пул даёт N/A для всех метрик. Полностью размеченный непустой пул из нулей даёт Precision = 0, Recall = N/A, nDCG = N/A. Если в пуле есть релевантные, но выдача пуста, все три метрики равны 0.

Если хотя бы одна оценка отсутствует, pending, спорна или принятая положительная запись не содержит доказательств, весь запрос получает N/A. Неразмеченные новости не удаляются из пула и не становятся нерелевантными. Политика строгая: она предотвращает сравнение на удобной подвыборке известных оценок.

Агрегат и показатели по компании — макросреднее по применимым запросам. Для каждой метрики приводится число вошедших запросов. Например, запросы без релевантных участвуют в Precision, но не в Recall. Частичное покрытие набора всегда показано отдельно. Оба алгоритма используют одинаковые применимые запросы. Попарная точность в этом этапе не реализована.

## Отраслевой baseline

Используется только `hooks.matching_profile.okved_codes` компании и `okved_codes` события. Код компании должен начинаться с области события: широкая область может покрывать узкий код, обратное предположение не делается. Среди совпавших событий первыми идут свежие публикации, затем event_id. Неизвестная дата идёт после известных. Если отрасль неизвестна, выдача пуста.

Baseline не использует финансы, платежи, группы, relevance_priors, банковские продукты, роль пользователя, обязательность или срочность. Проверка структуры MLView и события остаётся общей. Само отраслевое совпадение берётся из метаданных и не требует подтверждения механизма цитатой: это намеренно простой сопоставляемый алгоритм.

Оба алгоритма получают один и тот же полный tuple нормализованных кандидатов, до собственной фильтрации. Время оценки фиксировано запросом. Будущие публикации и профиль с датой позже момента оценки отвергаются для обеих систем.

## Формат набора

Это внутренний формат оценки `ml3a-1`, не новый Backend API и не изменение существующих JSON Schemas. Проверка формата реализована в `dataset.py`.

Корневые поля обязательны:

| Поле | Содержание |
|---|---|
| format_version | `ml3a-1` |
| dataset_id, dataset_version | Идентификатор и неизменяемая версия набора |
| kind | `synthetic_demo` или `real` |
| status | Для real: awaiting_independent_annotation, collecting_annotation, annotated; для демонстрации: synthetic_demonstration |
| labeling_provenance | method, independent_of_ranker, description |
| contexts | Замороженные MLView и необязательные полные профили |
| events | Нормализованные события, хеши и разделение выборки |
| queries | Контексты оценки и кандидатные пулы |
| annotations | Независимые записи рецензентов и решения арбитра |

Для реальных данных method = `independent_human`, для искусственных тестовых ожиданий = `synthetic_test_definition`. `independent_of_ranker` должен быть true. Это декларация происхождения, которую подтверждает команда, а не автоматическое доказательство независимости. Импорт оценок из выхода ранжировщика или единоличная LLM-разметка реального набора недопустимы.

Каждый context содержит `context_id`, `company_id`, `profile_version`, `ml_view`, `company_profile`, `ml_view_sha256`, `profile_sha256`, `provenance`. `profile_version` — существующий profile_id; версии и даты внутри контрактов должны совпадать. Без полного профиля company_profile и profile_sha256 равны null. `freeze_context` упаковывает готовые объекты, проверяя исходные схемы и согласованность через ML-2A. Он не строит новый профиль. Одно company_id/profile_version не может обозначать два разных снимка.

Запись events содержит `event` в существующем внутреннем NewsEvent, `sha256`, `event_group_id`, `split`. `freeze_event` создаёт контейнер снимка. Все события реального набора должны иметь synthetic = false; искусственный набор — true. Хеш SHA-256 вычисляется по UTF-8 JSON с sort_keys, без пробелов, ensure_ascii=false, allow_nan=false. Хеши проверяются перед запуском, профиль и event_id не подменяются.

Запрос содержит `query_id`, `context_id`, `company_id`, `analytic_focus` (CFO, CEO или null), `split`, `as_of` (ISO datetime с часовым поясом), `candidate_event_ids`. Повторные запросы одного контекста/фокуса/части и повторные пары компания–версия–фокус–событие отвергаются. Одна компания может иметь отдельные CFO/CEO-запросы и разные замороженные версии профиля.

Поля записи annotations перечислены в [пустом шаблоне](templates/annotation.json). Пустые идентификаторы этого отдельного бланка нужно заполнить перед включением в набор. `relevance_grade`, `relevance_reason` и `impact_mechanism` могут быть null у pending. Для reviewed/adjudicated нужны степень и содержательная причина; положительной степени нужен механизм. Отсутствующие доказательства положительной оценки отражаются в отчёте и блокируют её использование, не подменяясь выдуманными ссылками.

Допустимые ссылки supporting_evidence_refs:

```json
[
  {"kind": "article_quote", "event_id": "EVENT_ID", "evidence_id": "EXISTING_QUOTE_ID"},
  {"kind": "company_statement", "statement_id": "EXISTING_STATEMENT_ID"},
  {"kind": "ml_view_field", "path": "hooks.matching_profile.okved_codes"}
]
```

ID цитаты должен реально существовать в этой новости, ID утверждения — в замороженном полном профиле, путь — в MLView. Это проверка существования ссылки. Наличие HYPOTHESIS или поля MLView не делает их подтверждённым FACT; смысл и достаточность основания оценивает рецензент.

## Два рецензента и арбитраж

Каждый рецензент добавляет отдельную запись для той же query_id/event_id со своим reviewer_id. Дубли одного рецензента отвергаются. Pending не используется даже при заполненной степени. Для официальной оценки используются только reviewed или adjudicated с необходимыми данными.

Одна reviewed-оценка допустима форматом; для реальной контрольной выборки рекомендуется два независимых рецензента. Если степени совпали, выбирается запись с минимальным reviewer_id; все записи и причины сохраняются. Смысловое согласие разных формулировок программа не определяет. Совпадение степеней не заменяет бизнес-проверку причин; содержательный спор следует передать арбитру.

Если степени различаются, усреднения и голосования нет: результат `reviewer_conflict`, степень null. Арбитр добавляет третью запись с annotation_status = adjudicated и `adjudicates`, содержащим точный список всех reviewer_id проверенных оценок этой пары. Нужны минимум две рассмотренные оценки; исходные записи сохраняются. Два арбитражных решения одной пары отвергаются. Исправление разметки выпускается новой версией набора.

## Защита от утечки

Единица разделения — событие и его event_group_id, а не компания–новость. Все статьи об одном событии должны иметь одну группу и одну часть: development либо held_out. Запрос не может включить событие из другой части. Эти проверки выполняются для всего набора, даже если оценивается только одна часть.

Одинаковый непустой текст с разными ID также не может оказаться в разных группах/частях. Семантически похожие пересказы автоматически не распознаются: группировку должна проверить команда до замораживания. Хеши фиксируют содержимое, но не решают задачу понимания событий и не отслеживают сами по себе историю других версий набора.

Development используется для разработки и отладки. Held-out замораживается до просмотра результатов; запрещено подбирать по нему правила, веса и пороги. Для следующего изменения ранжировщика нужен отдельный цикл согласования и сохранённый контрольный пул. Все существующие новости ML-2A и демонстрация ML-3A относятся к development. Их нельзя объявлять независимой реальной контрольной выборкой.

## Содержание отчёта

JSON хранит версию набора, хеш полного входа, параметры метрик, хеши реализаций и схем, манифесты событий и профилей, происхождение разметки, статусы, разрешённые и спорные оценки. Для каждого запроса сохраняются общий пул и его хеш, обе выдачи, метрики, исходные объяснения ML-2A, расхождения позиций, false positives и false negatives относительно top-k. Отдельно считаются уникальные пары компания–событие и пары с учётом версии/фокуса.

False positive — выданное событие со степенью ниже бинарного порога. False negative — релевантный элемент кандидатного пула, не попавший в top-k. Эти примеры показываются только для полностью размеченного запроса. Пропуски доказательств и разметки сохраняются отдельно. В JSON N/A представлен null; русский Markdown использует строку N/A. Отчёт не содержит случайного времени генерации: повторение с теми же входами и кодом даёт те же файлы.

## Демонстрация

Используются неизменённые s1_MLView/s1_expected_profile и s3_MLView/s3_expected_profile. Восемь новостей из ML-2A дополнены явно синтетическим EVAL_LABOR о дефиците специалистов. Отдельный статический `examples/synthetic_annotations.json` задаёт 18 искусственных ожиданий без чтения выходов ранжировщика. Это не имитация выполненной человеческой разметки.

EVAL_LABOR намеренно проверяет покрытие существующих правил: условный кадровый механизм задан в тестовых ожиданиях, но ML-2A не поддерживает этот тип канала и исключает событие. Отраслевой baseline может показать метаданные без содержания, которые тестовые ожидания считают нерелевантными. Эти расхождения помогают проверить диагностику, а не доказывают превосходство алгоритма.

## Обнаруженный риск ML-2A

Детерминированность и сохранность фактических ID/цитат подтверждены локальными проверками. Семантическая верификация цитат ограничена лексическими проверками. Отдельная синтетическая диагностика 25.10.2026 воспроизвела следующий случай:

> Все организации с ОКВЭД 24.10 освобождены от обязанности до 2026-10-28 подавать сведения в реестр.

До исправления при ошибочных mandatory=true и applies_to_all_in_scope=true ML-2A с профилем s1 и as_of=2026-10-25T12:00:00+03:00 возвращал grounded/high. Слово «обязанности» проходило лексическую проверку, хотя текст сообщал об освобождении. Это воспроизвело существенный риск ложной подтверждённой срочности при противоречивой нормализации. Корректность ID цитаты не подтверждает смысл вывода.

Этот диагностический пример не добавлен к оценочному пулу и не используется для подбора правил. В этапе ML-3A ранжировщик не изменялся. Последующее целевое исправление добавило консервативную проверку смысловой согласованности: этот пример теперь получает grounded/normal с механизмом снижения нагрузки и отметкой о противоречии mandatory. Описание исправления и его ограничений находится в [SEMANTIC_HOTFIX.md](../ml_ranking/SEMANTIC_HOTFIX.md). Проверка ссылок в ML-3A по-прежнему не является семантической экспертизой; сложные нормы требуют независимой разметки и проверки человеком.

## Что подготовить Business/Product

1. Согласовать критерии степеней и порог релевантности с ML и Prompt Engineering. Разделять условный канал, подтверждённый факт и значимость для роли.
2. Предоставить реальные тексты и источники новостей, даты, существующие цитаты/ID и нормализованные поля без выдумывания пропусков. Собрать пул до просмотра выдач обоих алгоритмов, включая релевантные и нерелевантные кандидаты.
3. Получить от Backend готовые MLView и при необходимости полные профили. Зафиксировать profile_id, даты, хеши и происхождение снимков.
4. Назначить event_group_id всем связанным публикациям и заморозить разделение по событиям. Хранить неизменяемый набор и историю версий.
5. Выдать одинаковые профили, статьи и фокус двум рецензентам, скрыв выдачи, объяснения и метрики алгоритмов. Каждый независимо указывает степень, механизм, причину и существующие доказательства, затем ставит reviewed.
6. Передать разногласия отдельному арбитру. Зафиксировать reviewer_id и рассмотренные записи, сохранить исходные оценки. Не заполнять неизвестное оценкой 0.
7. Утвердить покрытие и достаточность выборки. Только затем выполнить отдельный реальный оценочный прогон. Маленькая выборка не обосновывает статистическую обобщаемость.

Новые зависимости не требуются: используются стандартная библиотека и уже установленные зависимости проверки контрактов. Существующие validate_all и лабораторный selftest следует выполнять во временной копии: они создают файлы фикстур и результаты прогонов.
