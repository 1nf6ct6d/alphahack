# ML-1A — исходящие платёжные признаки

Этот модуль рассчитывает признаки одной компании. Полный бизнес-профиль, ML-1B и ранжирование новостей сюда не входят. Схемы BCE не меняются.

## Запуск и публичная функция

Из корня проекта в PowerShell:

```powershell
.\.venv_win\Scripts\python.exe -B -X utf8 -m ml_features --company-id YOUR_COMPANY_ID --assume-additive-rows
.\.venv_win\Scripts\python.exe -B -X utf8 -m unittest discover -s tests -p "test_*.py" -v
```

По умолчанию CSV ищутся в `data/raw/`; параметры `--data-dir`, `--output-dir` и `--encoding` позволяют выбрать другие источники, папку отчётов и кодировку. CSV связей физических лиц на этом этапе не требуется. Код возврата `0` означает успешное выполнение в выбранном режиме, `2` — ошибку входных данных или запуска. Без флага `--assume-additive-rows` команда создаёт отчёт со структурными счётчиками и неизвестными денежными агрегатами.

Замените YOUR_COMPANY_ID в примерах на строковый ID из своей локальной выгрузки. Идентификаторы и финансовые показатели конкретных компаний в документации не публикуются.

Программное использование:

```python
from ml_features import compute_payment_features
from ml_features.serialization import serialize_derived_metrics

features = compute_payment_features(
    "YOUR_COMPANY_ID",
    "data/raw/df_Uid_data_hack.csv",
    "data/raw/df_Uid_payment_hack.csv",
    assume_additive_rows=True,
)
derived_metrics = serialize_derived_metrics(features)
```

Результат `PaymentFeatures` содержит точные значения `metrics`, получателей `recipients`, диагностику, исходные хеши и причины неопределённых величин. `serialize_features` формирует диагностический JSON, `serialize_derived_metrics` — только объекты существующего контракта, `write_reports` — JSON и Markdown. Публикации полного CompanyBusinessProfile нет.

Отчёты сохраняются как `reports/ml1a_payment_features_YOUR_COMPANY_ID.json` и `.md`. Шаблон этих файлов исключён через `.gitignore`. Для других ID имя строится безопасно без вложенных путей. Временных меток в содержимом нет: результат зависит от входных байтов, ID, режима и версии алгоритма. Источники проверяются по SHA-256 после чтения; изменение CSV во время расчёта останавливает его.

Платёжный файл читается построчно. В памяти находятся справочник ML-0 и записи/счётчики только выбранного плательщика; больших объединённых таблиц и размножения строк через join нет. Повторный вызов для другой компании снова читает файлы; пакетный пересчёт не реализуется в ML-1A.

## Определения, принятые до реализации

Строка компании — точное строковое совпадение PAYER с запрошенным ID. Пропуски распознаются по правилам ML-0. Денежное значение пригодно, если PAY_AMT является конечным неотрицательным числом. Нулевые суммы допустимы. Пригодный PAY_CNT — конечное неотрицательное целое число.

| Показатель | Определение |
|---|---|
| Все пригодные исходящие суммы | Сумма пригодных PAY_AMT во всех строках PAYER = company_id, включая самоплатежи и строки без ID получателя |
| Пригодная внешняя исходящая сумма E | Сумма пригодных PAY_AMT с непустым BENEFICIARY, отличным от PAYER. ID вне справочника и технические ID включены |
| Количество внешних платежей | Сумма PAY_CNT в строках, вошедших в E. Если хотя бы один PAY_CNT в этом наборе непригоден, итог неизвестен; известная частичная сумма показывается отдельно |
| Уникальные внешние получатели N | Число разных BENEFICIARY в строках, вошедших в E, включая получателей нулевых сумм |
| Получатели с однозначным профилем K | Число получателей из N, для которых все записи справочника совпадают после нормализации маркеров пропуска. U_428697 всегда считается техническим неоднозначным ID |
| Top-1 | Максимальная сумма одному получателю / E |
| Top-5 | Сумма пяти наибольших сумм получателям / E; если получателей меньше пяти, используются все |
| HHI | Сумма квадратов сумм получателям / E², что эквивалентно сумме квадратов точных долей. Округлённые доли не используются |
| Внутригрупповая доля | Подтверждённая сумма той же группе / E, только если денежная принадлежность всех внешних сумм определена. Иначе точная доля неизвестна; отдельно показываются подтверждённая нижняя граница, верхняя граница и неизвестная часть |
| Покрытие справочником | K / N. Знаменатель — все уникальные получатели пригодных внешних сумм. Дополнительно: сумма однозначным получателям / E |
| Самоплатежи | Число всех строк PAYER = BENEFICIARY = company_id и сумма пригодных PAY_AMT в них. Сумма неизвестна, если такие строки есть, но ни одной пригодной суммы нет |
| Нераспределённая сумма | Пригодные PAY_AMT со значением-пропуском BENEFICIARY. Внешнее назначение и принадлежность группе неизвестны |

Все денежные показатели относятся к пригодной части выгрузки. Если в некотором наборе есть строки, но все суммы непригодны, его сумма неизвестна, а не равна нулю. Для пустого набора сумма равна нулю. При нулевом знаменателе доля равна `null` с причиной. Строки неправильной длины и отсутствие обязательных столбцов останавливают расчёт: частичный файл не выдаётся за полный.

При включённом суммировании выполняется равенство: все пригодные исходящие суммы = пригодные внешние суммы + пригодные самоплатежи + нераспределённая пригодная сумма. Для этого контрольного равенства используются точные суммы пригодной части, включая нулевые суммы пустых пригодных наборов; они не подменяют неизвестные значения публичных показателей.

## Аддитивность и качество данных

По умолчанию суммирование отключено. Для расчёта денежных агрегатов и суммы PAY_CNT вызывающий код должен явно передать `assume_additive_rows=True`, а CLI — флаг `--assume-additive-rows`. Это допущение, что строки представляют аддитивные, не перекрывающиеся наблюдения; оно не является подтверждением организаторов. Условие сохраняется в отчёте, надёжность сумм и концентраций не объявляется безусловно высокой. Без флага остаются структурные счётчики и покрытие по уникальным получателям, денежные агрегаты неизвестны.

Повторные пары агрегируются суммированием только при этом допущении. Точные дубликаты также остаются в суммах и явно отмечаются; автоматического удаления нет. По самому CSV нельзя доказать, что совпавшие строки являются разными наблюдениями. Непригодные суммы исключаются с явными причинами; неизвестный ID получателя не исключается, если ID непустой.

Группа считается подтверждённой только у однозначного профиля с непустым GROUP_ID. Любой конфликт профиля, отсутствие компании, пропуск GROUP_ID или технический U_428697 оставляют принадлежность неизвестной. Совпадение GROUP_ID не доказывает контроль собственности, зависимость или отношения поставки. Неизвестная принадлежность никогда не становится подтверждённой другой группой.

PAY_AMT выражен в RUB. Известно начало наблюдений 1 января, год и окончание периода неизвестны. Даты, назначения платежей и поставщики не выводятся.

## Контракты и точность

Расчёт отделён от сериализации. Числовой разбор, кодировки, маркеры пропуска и выявление конфликтов переиспользуются из ML-0. Денежные входы разбираются через Decimal, арифметика сумм и долей выполняется точно через Fraction. Преобразование долей в JSON-числа и округление для человека происходят только на границе вывода; денежные суммы в диагностическом JSON записываются точными десятичными строками.

В DerivedMetric используются только существующие имена: `counterparty_count_out`, `top1_counterparty_share_out`, `top5_counterparty_share_out`, `hhi_out`, `intragroup_share_out`, `counterparty_coverage_in_df_uid`. Денежные суммы, сумма PAY_CNT, границы внутригрупповой доли и диагностические счётчики остаются в отдельной структуре. Имя `payments_count_total` не используется для суммы исключительно внешних исходящих PAY_CNT: такая область показателя пока не закреплена контрактом.

Top1 и top5 теперь содержат существующее поле breakdown с фактическими ID выбранных получателей и долями от полной пригодной внешней суммы. HHI содержит доли всех получателей; HHI равен сумме их квадратов. Неизвестные получатели не удаляются, top5 не перенормируется, равенства сумм разрешаются по строковому ID. При неопределённой доле breakdown отсутствует. Диагностика статуса получателя остаётся в serialize_features, не внутри DerivedMetric. Версия формирования D-ID — ml1a-1.1.0, она указана в derived_metrics_version; диагностический report_version сохранён. Сериализаторы доступны также из ml_features. Подробности и реальные проверки YOUR_COMPANY_ID — в [финальной передаче](../docs/ML_BACKEND_HANDOFF_FINAL.md).

`inputs` ссылается на реально наблюдавшееся поле PAYER с фактическим company_id. Это определяет выборку исходных строк. Для внутригруппового расчёта добавляется фактически подтверждённый GROUP_ID компании, если он известен. Полный источник вычисления — SHA-256 CSV, реальные имена используемых столбцов, фильтры, правила исключений и диагностика получателей. Несуществующих ID платежей и фиктивных значений evidence нет. Если строк PAYER = company_id нет, DerivedMetric не публикуются, поскольку наблюдаемого платёжного основания нет; диагностические счётчики остаются доступны.

Поле `coverage` у концентраций — доля пригодных денежных строк среди внешних строк с непустыми ID. У внутригрупповой доли — доля суммы с подтверждённой принадлежностью группе. У покрытия справочником — доля пригодных денежных строк, на которых определён набор получателей. Неизвестные компании не снижают полноту денежных данных: они влияют на отдельный показатель покрытия справочником.

`data_reliability` не является вероятностью. Консервативное правило этого этапа: не выше `medium`, поскольку период и аддитивность не подтверждены полностью; `low`, если значение неизвестно либо среди исходящих строк есть исключённые денежные значения. Это техническая маркировка ограничений, не результат калибровки модели.

Для проверки схем используются установленные зависимости `requirements-dev.txt`; сам расчёт требует только стандартную библиотеку Python 3.11+. ML-0, исходные CSV, существующие схемы и фикстуры не меняются. Старые проверки контрактов следует выполнять во временной копии: `tests/validate_all.py` пересоздаёт фикстуры, а `bce_lab selftest` создаёт локальные результаты.

Групповые признаки ML-1B и повторное использование готовых платёжных агрегатов описаны в [README_GROUPS.md](README_GROUPS.md). Публичная функция `compute_group_features` не меняет поведение ML-1A.
