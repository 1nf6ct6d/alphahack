## 2. Архитектура (изменения относительно v0.1)

Принцип сохранён: **код считает, LLM интерпретирует, валидатор проверяет** [ПРЕДЛОЖЕНИЕ].

```
CSV → 1 Ingest/Normalize → 2 Field States + Quality Auditor → 3 Feature Calculator
    → 4 Sector KB lookup (кэш) → 5 Hypothesis Generator (LLM, 1 вызов) → 6 Validator (+1 retry)
    → 7 Assembler (стабильные id, hash, local_id_map) → хранилище → проекции (ML/Interpreter/UI)
```

Что изменилось:
1. Состояние качества данных (`usability`) и режим обработки (`pipeline_mode`) — **две независимые оси**, связаны явной матрицей (раздел 4).
2. LLM возвращает только `hypotheses`, `sensitivities`, `conflict_notes`, `self_check`. Достоверность данных и итоговую уверенность считает код (раздел 7).
3. Модель получает `evidence_index` — закрытый список допустимых ссылок; всё, что вне индекса, валидатор отбрасывает.
4. `factor` берётся из закрытого каталога `factor_catalog` (общий словарь с ML), а не придумывается моделью.
5. Таблицы и справочники, которых в ТЗ нет (классификатор ОКВЭД, словари градаций), подключаются как опциональные: правила, которым они нужны, помечаются `requires_dictionary` и не считаются «пройденными», пока справочник не загружен.

Выбор моделей [ПРЕДЛОЖЕНИЕ, фиксируется после замера на реальных ключах]: базовая — Qwen3.6 35B A3B; эскалация при ≥2 конфликтах — GLM-5.3-Flash (ТЗ: «повышенной сложности»); Gemma 4 26B A4B — простая классификация; для экспертного LLM-judge — DeepSeek-V4.1-Flash. Router по правилам, не LLM-ом.

## 4. Состояния: `usability`, `pipeline_mode`, ОКВЭД, поля

Все определения — [ПРЕДЛОЖЕНИЕ]; пороги подлежат согласованию (D2).

### 4.1 `input_quality.industry_identification.status`

| status | Условие | Допустимо ли строить отраслевые гипотезы |
|---|---|---|
| `confirmed` | код есть и найден в классификаторе, название (если есть) ему соответствует | да |
| `code_only_unverified` | код есть, правильного формата, но проверить по классификатору нельзя (классификатор не загружен) или название отсутствует | да, с `dictionary_unconfirmed` в `uncertainty_sources`, `data_reliability` не выше medium |
| `ambiguous` | код и название указывают на разные виды деятельности (правило CONF-OKVED-NAME-MISMATCH) | да, но код приоритетнее; `data_reliability`=low; `usability` не выше `limited` |
| `name_only_unmapped` | кода нет, название есть, однозначно сопоставить с кодом нельзя | нет → `unusable`. LLM не подбирает код (правило против выдумывания) |
| `missing` | нет ни кода, ни названия | нет → `unusable` |
| `invalid` | код неправильного формата или отсутствует в классификаторе | нет → `unusable` |

### 4.2 `usability` (готовность данных)

Сигнальные группы (`signal_groups`): `scale` (выручка с подтверждённой семантикой **или** штат), `payments` (есть строки платежей после исключения аномалий), `bank_products` (клиент действующий и флаги не в конфликте), `foreign_trade` (`FTS_FLAG` известен и не в конфликте), `group_structure` (`GROUP_ID` известен). Географию в группы не включаем: регистрация — слабый признак.

| usability | Условие | Что разрешено |
|---|---|---|
| `unusable` | industry status ∈ {missing, invalid, name_only_unmapped} | только `facts`, `missing_data`, `input_quality`; гипотез нет; LLM не вызывается |
| `sector_only` | industry status не из unusable и число сигнальных групп = 0 | только темы `business_model`, `demand_side`, `regulation_exposure`, отраслевые |
| `limited` | сигнальных групп 1–2, либо industry status = `ambiguous` при ≥1 группе | все темы, поддержанные данными |
| `full` | ≥3 групп и industry status ∈ {confirmed, code_only_unverified} | все темы |

Проверка по матрице реализована в схеме профиля (`allOf` с `if/then`): `unusable` ⇒ гипотез нет и `pipeline_mode=no_inference`; `sector_only` ⇒ допустимые темы ограничены.

### 4.3 `pipeline_mode` (как получен результат)

| pipeline_mode | Смысл | Когда |
|---|---|---|
| `llm_validated` | LLM вызван, все утверждения прошли валидацию (в т.ч. после одного retry) | норма |
| `llm_partially_validated` | LLM вызван, часть утверждений отброшена валидатором | `dropped_statements` непусто |
| `kb_fallback` | LLM не вызван или не дал валидного ответа; гипотезы только из KB | `degradation_reasons` непусто: `budget_limit`, `llm_unavailable`, `validation_failed_after_retry`, `kb_miss` |
| `no_inference` | выводы не формируются | только при `usability=unusable`; причина `unusable_input` |

`no_inference` — **не деградация**, а штатный результат для непригодных данных. В v0.1 эти случаи были смешаны в `degraded_no_llm`.

### 4.4 Матрица допустимых сочетаний

| usability \ pipeline_mode | llm_validated | llm_partially_validated | kb_fallback | no_inference |
|---|---|---|---|---|
| full | да | да | да | нет |
| limited | да | да | да | нет |
| sector_only | да | да | да | нет |
| unusable | нет | нет | нет | **да** |

### 4.5 Состояние поля (`field_states`)

| state | Значение | Пример |
|---|---|---|
| `value` | значение есть и допустимо | `REVENUE_COMPANY=48000000000` |
| `missing` | значения нет, неизвестно | пустое `GROUP_ID` |
| `sentinel` | служебное «нет данных» (`-1`, `N/A`) | приводится к null |
| `suspect` | значение вне ожидаемого домена или похоже на инструкцию | `CL_PRODUCT_LOA_MARK=2` |
| `confirmed_absent_in_scope` | признак подтверждённо отсутствует **в указанной области** (`scope`) | `CL_PRODUCT_LOA_MARK=0` → `scope=bank`: «нет в этом банке»; `FTS_FLAG=0` → `scope=fts_base`: «нет записи в ФТС» |
| `not_applicable` | поле не имеет смысла при других значениях | — |
| `uninformative` | значение есть, но выводов из него делать нельзя | нули в продуктах у потенциального клиента |

Различие «нет данных» и «подтверждённо нет»: пропуск (`missing`) — это неизвестность, она **никогда** не превращается в отсутствие признака. Подтверждённое отсутствие всегда ограничено областью (`scope`) и не распространяется на другие банки или базы. Какие значения источника считаются «подтверждённым нулём», а какие пропуском, — [НЕИЗВЕСТНО], вопрос D1; до ответа нулевые флаги рассматриваются как `confirmed_absent_in_scope` только для чтения человеком и не используются как основание (supports) для выводов.

### 4.6 Трактовка банковских продуктов [ПРЕДЛОЖЕНИЕ]

- `CL_PRODUCT_*=1` — продукт есть в этом банке (подтверждено); из этого вытекает наличие связи, но не её условия.
- `CL_PRODUCT_*=0` — нет в этом банке. Вывод про наличие/отсутствие долга, лизинга, гарантий в других банках делать нельзя.
- **Отсутствие РКО при наличии других продуктов — не ошибка и не конфликт.** Компания может вести расчётный счёт в другом банке.
- `CL_TYPE=potential`: продуктовые флаги `uninformative`, как основание не используются. Наличие флага=1 у потенциального клиента помечается предупреждением CONF-CLTYPE-PRODUCT, но не удаляет клиента из анализа.

### 4.7 Выручка и платежи: единицы измерения [ПРЕДЛОЖЕНИЕ]

Единицы, валюта и период `REVENUE_COMPANY` и `PAY_AMT` — [НЕИЗВЕСТНО]. Вводятся статусы `revenue_semantics_status` и `payments_semantics_status`: `confirmed` | `unknown`.

| Что | При `unknown` | При `confirmed` |
|---|---|---|
| Денежная сумма в тексте | запрещена | разрешена в подтверждённых единицах |
| Сравнение выручки с порогом 15 млрд ₽ [ТЗ, стр. 4] | не выполняется; `target_segment_applicability=unknown` | `within_target` / `below_target` |
| Метрики `unit_free` (доли, HHI, число контрагентов, `payments_net_flow_ratio`) | разрешены | разрешены |
| Метрики `requires_confirmed_unit` (`size_class`) | значение null или метрика не публикуется | разрешены |
| Однородность единиц `PAY_AMT` между строками | считаем допущением, фиксируем `unit_unknown` в `uncertainty_sources` | — |
| `scale` как сигнальная группа | не засчитывается по выручке (только по штату) | засчитывается |

Выручка ниже 15 млрд ₽ **не считается ошибкой данных** [требование автора проекта; ТЗ определяет «крупный бизнес» как >15 млрд, стр. 4]. Это ограничение применимости к целевому сегменту: `target_segment_applicability=below_target`, `usability` не снижается, конфликт не создаётся. Интерфейс может показать мягкое предупреждение.

## 5. Правила для отсутствующих данных

| Что отсутствует | Влияние | Чего нельзя делать | Результат |
|---|---|---|---|
| ОКВЭД: код и название | blocking | любые отраслевые выводы | `unusable`, `no_inference` |
| Код есть, названия нет | minor | — | `code_only_unverified` или `confirmed` (если классификатор позволяет восстановить) |
| Только название | blocking, если не сопоставлено | подбирать код моделью | `name_only_unmapped` → `unusable` |
| Выручка | major | `size_class`, утверждения о масштабе | `signal_groups.scale` по штату, иначе false |
| Единицы выручки/платежей | см. 4.7 | денежные суммы, пороги | `unknown` |
| Платежи | major для supply_chain, demand_side | утверждения о структуре контрагентов | темы не генерируются |
| `CL_TYPE` | major | интерпретировать продуктовые флаги | `customer_status=unknown`, `bank_products=false` |
| `FTS_FLAG` | minor | гипотезы о внешней торговле по ФТС | `foreign_trade=false` |
| `GROUP_ID` | minor | групповые метрики; утверждать «независимая компания» | `group_structure=false` |
| `NEGATIVEMARK` | нет влияния | интерпретировать | `missing_data.kind=semantics_unknown` |

Общие принципы: нет данных — нет вывода; конфликт снижает достоверность, а не выбирается молча; `missing_data[].request_suggestion` подсказывает пользователю, что уточнить.

## 6. Реестр противоречий

Файл: `rules/conflict_rules.v2.json`. `data_conflicts` содержит только **противоречия между полями или источниками**; аномалии отмечаются отдельным `kind`.

| rule_id | kind | Условие | Нужен справочник |
|---|---|---|---|
| CONF-OKVED-NAME-MISMATCH | hard_contradiction | код найден, название ему не соответствует | классификатор ОКВЭД |
| CONF-FTS-FLAG-COUNTRY | hard_contradiction | `FTS_FLAG=0`, но `FTS_COUNTRY_NAME` заполнено | нет |
| CONF-CLTYPE-PRODUCT | source_disagreement | `CL_TYPE=potential`, но есть `CL_PRODUCT_*=1` | нет |
| CONF-PAY-SELF | anomaly | `PAYER == BENEFICIARY` | нет |
| CONF-STAFF-SOURCES (не MVP) | source_disagreement | градации ФНС и СПАРК не соседние | порядок градаций |
| CONF-REGION-CITY (не MVP) | hard_contradiction | город не принадлежит региону | справочник |

Исключено из v0.1 и почему — в `removed_from_v0_1` того же файла: порог выручки, отсутствие РКО, «нет продуктов у существующего клиента», возраст/стадия без словаря, внутригрупповые платежи (это ограничение интерпретации, не конфликт), покрытие контрагентов (это метрика), `NEGATIVEMARK` (это неизвестная семантика), пустая страна при `FTS_FLAG=1` (это пропуск).

## 7. Модель уверенности

В v0.1 «уверенность» была одной величиной и зависела от числа подтверждающих признаков. Теперь три раздельных аспекта [ПРЕДЛОЖЕНИЕ]:

| Аспект | Вопрос | Кто определяет | Значения |
|---|---|---|---|
| `data_reliability` | насколько надёжны исходные данные, на которых стоит вывод | **код** | low / medium / high |
| `inference_support` | насколько обоснован сам экономический вывод | **LLM** (по критериям), проверяется экспертом | weak / moderate / strong |
| `uncertainty_sources` | что именно неизвестно | **LLM** (закрытый список), минимум 1 пункт | см. схему |

`overall_confidence` вычисляет код, детерминированно.

**data_reliability** = минимум по `evidence` с `role=supports` из данных компании. Надёжность отдельного признака: `high` — значение чистое, без конфликтов; `medium` — код ОКВЭД без проверки по классификатору, либо метрика с покрытием <0,7; `low` — признак участвует в hard_contradiction/critical-конфликте либо покрытие <0,3. Записи `kb` на надёжность данных не влияют. `limits`-ссылки не снижают, но показываются.

**inference_support** — по смыслу, а не по числу признаков:
- `strong` — механизм общепринят и прямо следует из подтверждённой семантики поля (подтверждённая кредитная связь → чувствительность стоимости заимствований к ставке). Сила воздействия остаётся неизвестной;
- `moderate` — типично для отрасли по KB или правдоподобно, но применимость к компании не подтверждена;
- `weak` — цепочка из ≥2 умозаключений или косвенный признак.

**overall_confidence (гипотеза)** = `min(data_reliability, map(inference_support))`, где weak→low, moderate→medium, strong→high; затем, если среди `uncertainty_sources` есть любой из {`source_conflict`, `sector_generalization`, `dictionary_unconfirmed`, `unit_unknown`, `currency_unknown`, `low_coverage`}, итог не выше `medium`.
**overall_confidence (чувствительность)** = `min(overall_confidence оснований, data_reliability, потолок по uncertainty)`.

Следствия: много признаков уверенность не повышают; `high` возможна только при высокой надёжности данных, сильном механизме и отсутствии перечисленных источников неопределённости; уверенность не говорит о величине эффекта (она неизвестна).

Веса для ML: `weight = strength_score × confidence_score` (strength: 0,33/0,66/1,0; confidence: 0,25/0,55/0,8). Это **порядковый априор, не вероятность** (в схеме `weight_semantics="ordinal_prior_not_probability"`); ML вправе калибровать (D8). Константы — [ПРЕДЛОЖЕНИЕ], взяты как стартовые.

**Проверяемая связь гипотеза → данные.** Каждая гипотеза и чувствительность имеет 1–8 `evidence`: `{source, ref, value, role}`; `ref` обязан присутствовать в `evidence_index`, `value` — совпадать. Хотя бы одна запись `supports` должна быть из данных компании (не только `kb`). Числа в тексте гипотезы должны присутствовать среди `value` её evidence. Эти условия проверяет код (раздел 8), схема сама их выразить не может.

## 8. JSON-схемы и валидатор

Файлы (все JSON Schema Draft 2020-12, без комментариев):

| Файл | Назначение |
|---|---|
| `schemas/common.v1.schema.json` | общие определения: перечисления, `EvidenceRef`, типы идентификаторов |
| `schemas/llm_hypotheses_output.v1.schema.json` | единственный объект, который формирует LLM |
| `schemas/company_business_profile.v1.schema.json` | полный профиль (формирует Assembler) |
| `schemas/profile_views.v1.schema.json` | `MLView`, `InterpreterView`, `UIView` — проекции профиля |

Ключевые исправления: каждый объект определён самостоятельно с `additionalProperties:false` (без `allOf` с `properties` рядом, из-за которого v0.1 отклонял корректные объекты); условные ограничения матрицы состояний выражены `if/then`; значения `evidence` — скаляры; ответ LLM не содержит кодовых полей (`id`, `epistemic_status`, `generated_by`, `data_reliability`, `overall_confidence`).

**Валидатор (код) — обязательные проверки сверх схемы:**
1. каждая `ref` из `evidence` есть в `evidence_index`, `value` совпадает;
2. хотя бы один `supports` из company-источников;
3. `factor` ∈ `factor_catalog`;
4. числа в тексте ⊆ значений evidence; нет денежных сумм/порогов при `unknown` (4.7);
5. темы при `sector_only` допустимы;
6. `conflict_id` и `affected_local_ids` существуют; `basis_hypothesis_ids` существуют;
7. нет `supports` по нулевому флагу банка и по флагам потенциального клиента (4.6);
8. нет гипотез с confidence выше low, опирающихся на поле из critical-конфликта;
9. вычисление `data_reliability`/`overall_confidence` по разделу 7 — только в коде.
Нарушивший элемент попадает в `provenance.validation.dropped_statements` с причиной; при наличии отброшенных — `llm_partially_validated`; если ответ непригоден — один retry с описанием ошибок, затем `kb_fallback`.

### 10.3 Типы и передача неопределённости (общие правила)

1. Уверенность — только перечисление `low|medium|high`. Числа-«вероятности» не передаются; единственное число — `weight`, помеченное как порядковый априор.
2. Неопределённость **не схлопывается**: рядом с `overall_confidence` всегда идут `data_reliability`, `inference_support` (для гипотез) и `uncertainty_sources`.
3. Любой потребитель обязан сохранять `epistemic_status` утверждения и не повышать уверенность.
4. Для пропущенных значений используется `null` + `field_state`, не 0, не пустая строка.
5. Уверенность в механизме не означает знание величины эффекта; величина в BCE не оценивается.

### 10.6 Безопасность [ПРЕДЛОЖЕНИЕ; для прототипа достаточно описания, ТЗ стр. 12]

- Доступ к профилю только пользователям этой компании (по ролям); служебные поля (`trace_id`, `input_hash`) только сервисам.

Изменения по сравнению с v0.1: S3 теперь `sector_only` (раньше ошибочно `limited` при противоречии с правилом промпта); S5 теперь `no_inference` как штатный режим, не «деградация»; из S2 убраны проверки, невыполнимые без словарей (возраст/стадия, регион/город, градации штата), и конфликт по выручке <15 млрд; в сценариях использованы условные токены вместо «реалистичных» значений (города, страны).

### 12.2 Критерии качества [ПРЕДЛОЖЕНИЕ]

Автоматические (CI):

| Метрика | Целевое |
|---|---|
| Профили, валидные по схеме с первой попытки / после retry | ≥95 % / ≥99 % (после замера на реальных моделях) |
| Целостность evidence (все ссылки в индексе, значения совпадают) | 100 % (иначе элемент отбрасывается) |
| Гипотезы с supports-evidence из данных компании | 100 % |
| Числа в тексте не из evidence; денежные суммы при `unknown` | 0 |
| LLM-ответ содержит кодовые поля | 0 |
| Уверенность воспроизводится по разд. 7 (проверка кодом) | 100 % |
| Гипотезы выше low, опирающиеся на поле из critical-конфликта | 0 |
| Вывод об отсутствии долга из `LOA_MARK=0` | 0 |
| Устойчивость к инъекции | 100 % на adversarial-наборе |

Экспертные (BA, слепая оценка 20–30 профилей, шкала 1–5): релевантность, нетривиальность, обоснованность, честность неопределённости, полезность для матчинга. Порог приёмки и разметка — решаются командой (D6). Сквозная проверка: nDCG@5 ранжирования новостей с профилем против отраслевого baseline на размеченных парах (после появления News Relevance Engine) — прямая проверка критериев 01 и 05 ТЗ.

## 13. Проверки, выполненные при подготовке v0.2

Запуск: `.venv/bin/python tests/validate_all.py` (зависимость: `jsonschema==4.23.0`, `requirements-dev.txt`). LLM не вызываются.

**Выполнено:**
- все четыре схемы валидны по метасхеме Draft 2020-12, не содержат комментариев;
- структурный lint: нет конструкций вида `allOf`+`properties` рядом с `additionalProperties:false`; воспроизведён баг v0.1 на мини-схеме;
- 5 корректных профилей, 4 корректных ответа LLM, 15 проекций (MLView, InterpreterView, UIView) валидны;
- 22 заведомо некорректных примера отклонены схемами (лишнее поле, пустой evidence, неверные статусы и матрица состояний, неверная дата, неизвестная модель и т. д.);
- согласованность промпта и схемы: верхние поля ответа, темы `sector_only`, отсутствие кодовых полей в схеме LLM, плейсхолдеры и перечисления, отсутствие дрейфа терминов, сохранение ключевых запретов;
- пять сценариев: воспроизводимость уверенности, целостность evidence, числа и единицы, флаги банка, конфликты по реестру, id и ссылки, отсутствие инъекции;
- контроль чувствительности тестов: в копии проекта внесены 6 искусственных нарушений — каждое было поймано нужной проверкой.

**Ограничения этих проверок (важно):**
- ожидаемые профили сценариев написаны вручную; они доказывают, что контракты выразимы и согласованы, а не что движок их выдаст;
- проверка весов `relevance_priors` — самосогласованность, а не калибровка;
- согласованность промпта проверена структурно, не на поведении модели.

**Невозможно сейчас:**
- на реальных данных: нет CSV (покрытие пропусков, распределения, домены значений, покрытие контрагентов платежей, реальная частота конфликтов);
- на разрешённых LLM: нет доступа к ключу — не измерены соблюдение схемы, доля отброшенных утверждений, галлюцинации, токены и стоимость, качество на русском, устойчивость к инъекции на реальной модели;
- правила, требующие справочников: CONF-OKVED-NAME-MISMATCH, CONF-STAFF-SOURCES, CONF-REGION-CITY (справочников нет);
- экспертная оценка, калибровка уверенности, сквозной nDCG@5;
- работа API, хранилища и UI (не реализованы).
