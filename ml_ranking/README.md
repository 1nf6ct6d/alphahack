# ML-2A — детерминированная релевантность новостей

Базовый компонент для Backend: принимает существующий MLView, проверяет его по неизменённой JSON Schema и возвращает сериализуемые результаты. Это правила, а не обученная модель. Сбор новостей, LLM, RAG, эмбеддинги, сервер и публичный API здесь не реализуются.

## Использование

```python
from datetime import datetime
from ml_ranking import NewsEvent, rank_news
from ml_ranking.serialization import serialize_ranking

events = [NewsEvent.from_dict(item) for item in normalized_news]
results = rank_news(
    ml_view,
    events,
    company_profile=full_company_business_profile,
    analytic_focus="CFO",
    top_k=5,
    as_of=datetime.fromisoformat("2026-10-25T12:00:00+03:00"),
)
payload = serialize_ranking(results)
```

`company_profile`, `analytic_focus` и `as_of` необязательны. Без `as_of` срочность не подтверждается; системные часы не используются. `top_k` — верхняя граница, не требуемое количество новостей. Пустой релевантный набор возвращает `[]`. `classify_event` отдельно возвращает решение, включая `none`, для диагностики исключений.

MLView и полный профиль строит Backend. Модуль не создаёт новый формат профиля, не подменяет сборку BCE и не меняет MLView. ML-1A/ML-1B не подключаются напрямую: их метрики должен включить в согласованный профиль Backend.

## Границы доверия к профилю

Используются `jsonschema` и `referencing`, уже установленные через `requirements-dev.txt`. Проверяются существующие схемы MLView и CompanyBusinessProfile, конечность JSON-чисел, совпадение company_id, profile_id, даты, usability и hooks. Числовые признаки сверяются с реальными derived_id, именами, значениями, покрытием и надёжностью полного профиля. Повторные ID утверждений и неоднозначные ключи breakdown отвергаются.

Для подтверждённого основания требуются флаги `schema_valid` и `evidence_refs_verified` из provenance. Дополнительно проверяются FACT, состояние исходного поля, конфликты и надёжность. Эти флаги — доверенный результат предыдущей проверки Backend, а не независимый повторный аудит CSV ранжировщиком. Источник и стадия проверки явно названы в выходных ссылках.

Без полного профиля ОКВЭД из MLView остаётся непроверенным указанием: возможна `conditional`, но не `grounded`. `code_only_unverified`, критический конфликт или неподтверждённый provenance также не создают grounded. Гипотезы и sensitivities не повышаются до фактов. Ключевые слова, регион регистрации и relevance_priors сами по себе не создают релевантность. Веса имеют семантику `ordinal_prior_not_probability`; базовый ранжировщик не использует их как доказательства или числовой relevance score.

## Внутренний контракт события

`NewsEvent` и `ArticleEvidence` — внутренние типы ML-2A, не согласованный публичный контракт Backend. Поля: event_id, title, source_id, source_url, content, published_at, event_type, factor_classes, okved_codes, geography, entities, evidence. Для требований дополнительно нужны deadline, mandatory и applies_to_all_in_scope. Пропущенные флаги остаются `None`. `synthetic=True` явно маркирует учебные примеры; `False` не подтверждает подлинность источника.

Поддерживаемые типы: regulation_change, tax_change, input_cost_change, demand_change, monetary_policy_change, counterparty_disruption, other. Классы факторов берутся из существующей common-схемы. Идентификаторы организаций не разрешаются по названиям или догадкам; entities используются только как явно переданные точные ID.

Каждая цитата содержит переданный evidence_id, точный фрагмент content и список полей supports. Цитата должна входить в статью. ОКВЭД и ID участников сверяются с буквальными значениями цитаты. Регуляторные утверждения проходят отдельную консервативную проверку направления нормы, общего охвата и связи срока с действием. Освобождение не превращается в обязанность из-за mandatory=true; конфликт флагов блокирует high. Дата срока должна явно присутствовать в формате YYYY-MM-DD либо DD.MM.YYYY. Свободные формулировки дат не угадываются. Классификация event_type/factor_classes остаётся входом от нормализатора; эти проверки не заменяют полноценное понимание текста, проверку источника или юридическую экспертизу. Правила, ограничения и пример до/после описаны в [SEMANTIC_HOTFIX.md](SEMANTIC_HOTFIX.md).

published_at — ISO datetime с часовым поясом либо None, deadline — YYYY-MM-DD либо None. Будущая публикация относительно явно переданного as_of отвергается. Неизвестная дата не заменяется текущей. Повторяющиеся event_id отвергаются, а не выбираются произвольно. Семантическая дедупликация разных ID не входит в этот этап.

## Правила релевантности

| Событие | Основание | Результат |
|---|---|---|
| Изменение регулирования или обязательного отраслевого платежа | Подтверждённый FACT об ОКВЭД и поддержанные цитатой обязательность и применение ко всем организациям указанной области | grounded; размер эффекта и исполнение требования не утверждаются |
| Явное освобождение или отмена обязанности | Подтверждённая отраслевая область и связный фрагмент о снижении нагрузки | grounded/normal при подтверждённом основании компании и общем охвате; иначе conditional |
| Та же отрасль, но не подтверждена применимость или сам ОКВЭД | Явный ОКВЭД события и отраслевой канал | conditional с условиями проверки |
| Изменение цены ресурса или спроса | Явная отраслевая область и соответствующий класс фактора | conditional: использование ресурса, рынки сбыта и договоры неизвестны |
| Изменение денежно-кредитной политики | FACT банковского кредитного продукта действующего клиента | conditional: тип ставки, условия договора и рефинансирование неизвестны |
| Нарушение работы контрагента | Явный ID в новости и поддержанная DERIVED-платёжная связь в breakdown полного профиля, согласованная с MLView | conditional: платёжная связь не доказывает поставку, актуальность и значимость связи неизвестны |
| Только приор, ключевое слово, регион регистрации, неизвестный контрагент или заголовок без статьи | Поддержанного механизма нет | none; событие не попадает в персонализированный список |

ОКВЭД сопоставляется направленно: область события может быть шире кода компании, но узкая новость не применяется автоматически к широкому коду компании. Классификатор ОКВЭД модуль не загружает: статус подтверждения берётся из полного профиля.

Тексты interpretation_constraints передаются дословно. Известные ограничения по отсутствию данных, банковским флагам, денежным выводам и платёжным отношениям отражены в правилах. Произвольные новые ограничения в свободном тексте автоматически не интерпретируются и требуют отдельного согласования правил.

Географически ограниченное отраслевое событие остаётся conditional: регистрация в регионе не подтверждает операционное присутствие или применимость нормы. Отсутствующие списки и поля означают нехватку информации, а не подтверждённое отсутствие бизнес-связей. Исходные caveats использованных FACT/DERIVED сохраняются вместе со ссылками и ограничениями результата.

## Ранжирование и приоритет

Сортировка лексикографическая:

1. grounded перед conditional.
2. Подтверждённый приближающийся срок; среди таких событий более близкий срок первым.
3. Специфичность механизма: отраслевое обязательство, подтверждённая предпосылка финансирования, условный отраслевой канал, платёжная связь с неизвестной ролью.
4. Поддержанный механизмом ролевой фокус при прочих равных.
5. Свежесть публикации; неизвестная дата после известных.
6. event_id для стабильного разрешения равенства.

`high` возможен только у grounded обязательного отраслевого требования с надёжным FACT и подтверждённым сроком от текущей даты анализа до `urgency_horizon_days` включительно. Нужны связная поддержка источником и отсутствие противоречащих ему флагов; освобождение, отмена или неизвестное направление не создают high. Стартовый горизонт — 7 календарных дней, это явная настройка правил, не порог relevance score. Grounded без такой срочности получает normal, conditional — low. Истёкший срок сам по себе не доказывает нарушение или санкции.

CFO может поднять подтверждённый финансовый канал, CEO — операционный/стратегический. Фокус применяется только к grounded с проверенным основанием и после более важных критериев. Условные механизмы без достаточных данных не получают выдуманных ролевых различий. Фокус не меняет факты, цитаты, категорию релевантности или приоритет.

## Демонстрация и проверки

```powershell
.\.venv_win\Scripts\python.exe -B -X utf8 -m ml_ranking
.\.venv_win\Scripts\python.exe -B -X utf8 -m unittest discover -s tests -p "test_news_ranking.py" -v
```

Демонстрация использует существующие синтетические s1_MLView/s1_expected_profile и s3_MLView/s3_expected_profile без изменения файлов. Один и тот же набор из `examples/synthetic_events.json` применяется к металлургическому и ИТ-профилю. Все новости вымышлены, URL на example.invalid, момент анализа фиксирован по Москве. У ИТ-профиля ОКВЭД code_only_unverified, поэтому отраслевые результаты остаются условными.

Создаются `reports/ml2a_news_ranking_demo.json` и `.md`, исключённые через `.gitignore`. JSON содержит источник, цитаты, реальные ID утверждений профиля, условия, ограничения и факторы сортировки каждого результата. Числовые вероятности, оценки финансового эффекта и искусственные новости для заполнения top-k отсутствуют.

Тесты показывают поведение правил на синтетических случаях, не качество на реальных новостях. Размеченный отложенный набор и ML-3 не создаются. Существующие проверки контрактов следует запускать во временной копии, поскольку они пересоздают фикстуры.
